# Sloy Native · Tauri 2

Нативная версия использует существующий интерфейс из `dist/`, отдельный Rust-бэкенд и локальное хранилище Obsidian. `npm run native:prepare` создаёт `.native-web/`, оригинальный сайт не меняется.

## Запуск и сборка

Установите закреплённые версии инструментов командой `mise install` и зависимости Tauri для вашей ОС: https://v2.tauri.app/start/prerequisites/.

```
npm ci
npm test
npm run test:native
npm run test:rust
npm run native:dev
npm run native:build -- --no-bundle
```

Windows: MSVC Build Tools, WebView2. `npm run native:build -- --bundles nsis,msi` создаёт установщики в `src-tauri/target/release/bundle/`. Подпись релизов не настроена.

Arch: `sudo pacman -S --needed base-devel rust nodejs npm webkit2gtk-4.1 librsvg openssl`. Собирайте на Arch для его текущих библиотек. Инструкция PKGBUILD находится в `packaging/arch/`.

Android: JDK 21, Android SDK 36, NDK r28c, Rust target `aarch64-linux-android`. Укажите JAVA_HOME, ANDROID_HOME, NDK_HOME. Затем `npm ci`, `npm run android:init`, `npm run android:debug`. Для компактного тестового APK после сборки выполните `python3 scripts/compact-apk.py` (Linux, нужны JAVA_HOME, ANDROID_HOME, NDK_HOME).

Android-проект генерируется и не хранится в репозитории. Доступ к vault предоставляется через системный выбор папки и SAF; общий доступ к диску не требуется. Настоящую работу SAF необходимо проверить на устройстве и его файловом провайдере.

Исходник иконки приложения хранится в `src-tauri/icons/source.png`. После его изменения пересоздайте иконки для desktop, Android и iOS командой `npx tauri icon src-tauri/icons/source.png --output src-tauri/icons`. Веб-версия использует ту же иконку из `dist/assets/sloy-s.png`.

## CI и проверка перед слиянием

`.github/workflows/ci.yml` запускается на pull request в `main`, push в `main` и вручную через Actions → CI → Run workflow. Новый запуск отменяет предыдущий для того же PR или ветки.

На pull request выполняются `npm run check` (линтеры, форматирование конфигураций, проверки Rust-зависимостей и workflows, тесты frontend/native/Rust/Python) и Betterleaks для изменений PR. Сборки платформ выполняются только в release-пути. Дополнительный еженедельный workflow проверяет всю историю на секреты и lockfiles на известные уязвимости.

В release-пути собираются Windows NSIS `.exe`, Linux `.AppImage`, Arch build kit и Android ARM64 APK. Arch использует PKGBUILD и архив исходников проверяемого коммита; `makepkg` запускается от отдельного непривилегированного пользователя. В build kit лежат PKGBUILD, desktop-файл и исходники коммита. GitHub Release прикладывает артефакты автоматически.

После первого запуска в Settings → Rules → Rulesets для `main` добавьте обязательную проверку **CI passed** (источник GitHub Actions). На PR она требует тесты и secrets scan; в release-запуске также обязательны все четыре сборки. Включите Require a pull request before merging и Require branches to be up to date before merging. Список bypass должен быть пустым, если правила должны применяться и к владельцу репозитория. Изменения workflow сами по себе не включают защиту ветки.

CI не заменяет ручную проверку интерфейса и Android SAF на устройстве. Локальные проверки можно поставить командой `hk install`; перед коммитом проверяются staged файлы, перед push выполняется полный `npm run check`.

## Выпуск версии

`.github/workflows/release.yml` запускается при push тега `v*`. Тег должен указывать на коммит из истории `main`; поддерживается формат `vMAJOR.MINOR.PATCH`, например `v0.1.0`. Версии в `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, `src-tauri/core/Cargo.toml` и `packaging/arch/PKGBUILD` должны совпадать с тегом. При обновлении Cargo.toml обновите и соответствующие Cargo.lock. Проверить версии локально: `GITHUB_REF_NAME=v0.1.0 node scripts/check-release-version.mjs`.

В Settings → Secrets and variables → Actions должны быть repository secrets:

- `ANDROID_KEYSTORE_BASE64` — содержимое постоянного keystore в Base64;
- `ANDROID_KEYSTORE_PASSWORD` — пароль хранилища;
- `ANDROID_KEY_ALIAS` — имя ключа, например `sloy`;
- `ANDROID_KEY_PASSWORD` — пароль ключа.

Release повторно использует CI: выполняет тесты, собирает Windows, Linux и Arch, а для Android вместо debug собирает release APK. Затем `scripts/sign-android.py` выравнивает APK, подписывает постоянным ключом и проверяет подпись. Ключ декодируется во временный файл с правами 0600 и удаляется после подписи. Пароли передаются apksigner через переменные окружения. Секреты передаются только шагу подписи release-сборки; в PR этот шаг не выполняется.

После слияния изменений в `main` создайте и отправьте тег:

```sh
git switch main
git pull --ff-only
git tag v0.1.0
git push origin v0.1.0
```

После успешных тестов и всех сборок workflow создаёт черновик GitHub Release с `.exe`, `.AppImage`, Arch build kit `.tar.gz`, подписанным `.apk` и `SHA256SUMS`. Проверьте установку и работу на копии vault, затем нажмите Publish release. Windows-установщик пока не подписан. Первая установка release APK поверх preview с другим ключом потребует удаления preview; заранее сохраните локальные несинхронизированные данные.

При ошибке можно повторно запустить Release через Re-run failed jobs или Re-run all jobs. Существующий черновик обновляется; уже опубликованный релиз workflow перезаписывать отказывается. Автоматическая публикация и AUR не настроены.

## Первый запуск

Выберите Obsidian vault в настройках и проверьте имена папок. Существующие заметки вне этих папок приложение не меняет. Начинайте проверку на копии vault. С сайта можно перенести JSON через существующий импорт: сначала подключите vault, потом импортируйте резервную копию.

Папки по умолчанию:

- `Areas`: зоны и их самостоятельные задачи.
- `Projects`: проекты, подпроекты и собственные задачи.
- `Habits/Definitions`: определения привычек.
- `Habits/Records`: одна заметка на дату со всеми счётчиками.
- `Journals/Daily`, `Weekly`, `Quarterly`, `Yearly`: по одной заметке на период, план и факт вместе.
- `Knowledge`: заметки, которые учитываются в активности.

Заметки зон/проектов распознаются по папке, имени, заголовку и YAML `parent`. При записи получают `sloy_type` и `sloy_id`. Родитель задаётся wikilink, например `parent: '[[Areas/Работа]]'`. Вложенность: зона → проект → подпроект. Неоднозначные ссылки и повторяющиеся ID блокируют загрузку, сохраняя последнее корректное состояние.

Задачи — строки Obsidian Tasks `- [ ] ...`, `- [x] ... ✅ YYYY-MM-DD`, срок `📅`, повторение `🔁`, ID `🆔`, block ID. Задачи не дублируются чекбоксами в Journal: там обычные строки со ссылками. Sloy добавляет свои inline-поля и сохраняет даты создания/старта/планирования Tasks. Прочее содержимое заметок и неизвестные YAML-поля остаются свободными.

Поддерживаются простые повторения: every day/weekday/week/month/year, every N days/weeks/months/years, when done. Следующий экземпляр создаётся при завершении. Сложные правила Tasks сохраняются, но завершать такую задачу нужно в Obsidian. Календарная материализация повторов браузерной версии в нативном приложении отключена, чтобы не конкурировать с Tasks.

## Синхронизация и сверка

Syncthing работает отдельно, на каждом устройстве. Включите его локальный REST API и укажите URL (по умолчанию http://127.0.0.1:8384), Folder ID и API key. На Android нужен установленный и запущенный клиент Syncthing с доступным API. Приложение не запускает и не устанавливает Syncthing.

Ctrl+S или кнопка «Синхронизировать»: завершить локальные записи → запросить `/rest/db/scan` → дождаться idle/нулевой очереди и completion удалённых устройств → сверить vault. Отключённые устройства и таймаут показываются как частичная/неподтверждённая синхронизация. Force означает принудительное сканирование и сверку, а не overwrite/revert Syncthing. HTTPS проверяется; для собственного сертификата можно добавить PEM. Ключ хранится в локальных настройках приложения вне vault, не синхронизируется.

Метаданные проверяются при запуске, возвращении в приложение и каждые 60 секунд на переднем плане. Неизменившиеся заметки не перечитываются. Полная индексация нужна впервые или по кнопке перестройки. SQLite — восстанавливаемый локальный кэш, не источник данных и не часть vault.

Перед записью проверяется SHA-256 исходной версии. При конфликте запись блокируется, локальный черновик сохраняется в recovery-копии. Кнопка «Несохранённые изменения» позволяет прочитать копии и повторить запись либо перечитать vault, сохранив копии. Изменения нескольких файлов не являются одной файловой транзакцией: recovery позволяет вручную завершить операцию при сбое между файлами. Удалённые заметки перемещаются в `.trash/sloy`.

## Knowledge и завершение дня

Считаются только созданные заметки из Knowledge. Дата берётся из выбранного YAML-свойства, затем из filesystem birthtime, если оно доступно. Unix ctime не используется. Если дата отсутствует и ОС/SAF не предоставляет birthtime, заметка остаётся без даты и не входит в счётчик.

В настройках хранилища раскройте «Папки и даты». Внутри раздела «Типы заметок Knowledge» укажите корень заметок и выберите один способ определения типа: «По папкам» (по умолчанию) или «По свойствам». Показываются только поля выбранного способа. Настройки второго способа сохраняются при переключении. Значения по умолчанию:

| Тип | Подпапка относительно корня | Значение свойства `type` |
| --- | --- | --- |
| Цитаты | `Cites` | `quote` |
| Переосмысления | `Reflections` | `reflection` |
| Мои мысли и идеи | `Thoughts` | `thought` |

В режиме «По папкам» `Knowledge/Cites/Цитата.md` считается цитатой без свойства типа. Для заметок в общей папке выберите «По свойствам»; например, в `Knowledge/Заметка.md` можно указать:

```yaml
---
created: 2026-11-01
type: thought
---
```

Имена подпапок, имя свойства и его значения можно изменить под существующий vault, например на `вид: цитата`. В режиме «По папкам» свойства не учитываются; при вложенных правилах используется самая глубокая подходящая подпапка. В режиме «По свойствам» подпапки не учитываются, имя свойства обязательно. Пустая подпапка или пустое значение отключает правило для категории в соответствующем режиме. Значения свойства сравниваются без учёта регистра и пробелов по краям. Поддерживаются скалярные значения и списки Obsidian; если список содержит несколько разных распознанных типов, заметка относится к «Без типа». Каждая заметка учитывается ровно один раз; неподходящие под выбранный способ входят в «Без типа» и общий счётчик.

В Journal показаны общий счётчик и отдельные итоги по каждому типу за день, неделю, квартал и год. В аналитике доступны те же типы как отдельные метрики с дневными значениями и недельными суммами. Разбивка сохраняется в `sloy_knowledge.byType` дневной заметки и в `sloy_statistics.knowledgeByType` заметок периодов. Исходные заметки Knowledge при подсчёте не изменяются.

День закрывается логически в 23:59:59 выбранного часового пояса. Если приложение закрыто, запись факта выполняется при следующем запуске. Сохраняется последнее известное значение дня: точное состояние выключенного приложения восстановить невозможно. Закрытые дневные значения автоматически не пересчитываются после поздних синхронизаций. Из дневных записей собирается статистика недели, квартала, года; знаменатель продуктивности берётся из собственного снимка соответствующего плана.

Разбивка по типам фиксируется вместе с общим числом. Изменения правил или типов обновляют открытый день, сохраняя закрытую историю. Старые дневные факты без разбивки сохраняют исходное число в категории «Без типа»; типы задним числом не восстанавливаются по текущему состоянию файлов. При первом сканировании дат без сохранённых дневных фактов разбивка берётся из заметок. После обновления приложения или изменения правил индекс перестраивается автоматически; последующие сверки используют кэш типов без перечитывания неизменившихся заметок.

## Проверки и ограничения

Проект содержит проверки Markdown-преобразования, очереди записи, конфликтов, индексации и локального API. Сборка не заменяет тестирование на физическом Android, Windows и Arch. Веб-версия продолжает хранить свои данные в браузере и сама по себе к vault не подключается.

Проверки восстановления: 109 тестов исходного сайта, 17 тестов нативного адаптера и 10 Rust-тестов. Бенчмарк 10 050 заметок: около 0,9 с первая индексация, около 94 мс повторная; 0 чтений неизменившихся заметок. Время зависит от диска и Android-провайдера; это измерение на Linux, не обещание скорости телефона.
